# Метричний аналіз якості коду
## Лабораторна робота №8 — Варіант 7

## 1. Мета аналізу

Метою є порівняння якості початкової та рефактореної
версій системи медичної клініки за метриками:

- CBO (Coupling Between Objects);
- LCOM4 (Lack of Cohesion of Methods).

## 2. Аналіз початкового коду

### Клас LegacyClinicService

Клас LegacyClinicService містив основну логіку системи:
- зчитування даних користувача;
- створення пацієнта, лікаря та запису;
- розрахунок вартості консультації;
- розрахунок страхового покриття;
- формування квитанції;
- імітацію збереження запису;
- відправлення SMS.

CBO = 3.

Залежності:
1. Patient;
2. Doctor;
3. Appointment.

Клас Scanner не враховується, оскільки це системний тип Java.

LCOM4 = 1.

У початковому класі є лише один бізнес-метод
scheduleAppointmentConsole(), тому граф методів має
одну зв'язну компоненту.

Примітка: LCOM4 не відображає надмірну кількість обов'язків
усередині одного великого методу.

## 3. Аналіз рефактореного коду

### Appointment

CBO = 4.

Залежності:
1. Patient;
2. Doctor;
3. LabTest;
4. InsurancePolicy.

LCOM4 = 1.

Методи працюють зі спільним станом запису та взаємодіють
між собою. Бізнес-логіка зосереджена в сутності Appointment.

### Doctor

CBO = 1.

Залежність:
1. ConsultationPricing.

LCOM4 = 1.

Клас відповідає за дані лікаря та розрахунок вартості
консультації через відповідну стратегію.

### AppointmentController

CBO = 1.

Залежність:
1. AppointmentService.

LCOM4 = 1.

Контролер має одну відповідальність — передавання
запиту до сервісу сценарію запису.

### AppointmentService

CBO = 8.

Залежності:
1. AppointmentRepository;
2. SmsSender;
3. InvoiceGenerator;
4. InsurancePolicy;
5. Appointment;
6. Patient;
7. Doctor;
8. LabTest.

LCOM4 = 1.

Сервіс координує один сценарій — оформлення
та підтвердження запису пацієнта.

## 5. Інженерні висновки

Після рефакторингу бізнес-логіка була розподілена між
доменними сутностями та технічними компонентами.

Клас Doctor має низьке зчеплення (CBO = 1), а Appointment
відповідає цільовому показнику CBO ≤ 4.

AppointmentController має CBO = 8, тому цільове значення
для контролера поки не досягнуто. Це вказує на необхідність
подальшого зменшення кількості його залежностей.

Усі три проаналізовані рефакторені класи мають LCOM4 = 1,
що свідчить про функціональну згуртованість їхніх основних
бізнес-методів.

Загалом рефакторинг покращив розподіл відповідальностей,
інкапсуляцію та структуру системи, але контролер потребує
додаткового вдосконалення.
